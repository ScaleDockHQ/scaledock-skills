# Chapters V1 to V8

Read this when scoping, implementing or verifying the input, frontend, API, file, authentication, session and authorization chapters of ASVS 5.0.0. Each chapter lists its sections, its requirement count by level (from the 5.0.0 flat JSON), and its key requirements, paraphrased. The paraphrase is for orientation: copy the full requirement text from the official JSON or markdown into any requirement list, report or contract. Sources: the 5.0.0 chapter files `0x10` to `0x17` and the flat JSON, listed in [Sources](../SKILL.md#sources).

## V1 Encoding and Sanitization

30 requirements: 8 L1, 19 L2, 3 L3. Unsafe processing of untrusted data that an interpreter reads by its own syntax. Prefer safer APIs (parameterized queries, auto-escaping templates); input validation is defense in depth and lives in V2 (V1 Control Objective).

| Section                                     | Key requirements                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| V1.1 Encoding and Sanitization Architecture | `v5.0.0-1.1.1` (L2) decode to canonical form once, before validation. `v5.0.0-1.1.2` (L2) encode as the final step before the interpreter, or let the interpreter do it.                                                                                                                                                                                                                                                           |
| V1.2 Injection Prevention                   | `v5.0.0-1.2.1` (L1) context-relevant output encoding in HTTP, HTML and XML. `v5.0.0-1.2.2` (L1) encode untrusted data in URLs. `v5.0.0-1.2.3` (L1) encode when building JavaScript or JSON. `v5.0.0-1.2.4` (L1) parameterized queries or ORMs for SQL, HQL, NoSQL, Cypher. `v5.0.0-1.2.5` (L1) OS command injection. LDAP, XPath, LaTeX and regex escaping at L2 (`1.2.6` to `1.2.9`); CSV and formula injection at L3 (`1.2.10`). |
| V1.3 Sanitization                           | `v5.0.0-1.3.1` (L1) sanitize WYSIWYG HTML with a well-known library. `v5.0.0-1.3.2` (L1) avoid `eval()` and dynamic code execution such as SpEL. L2: SVG, Markdown, CSS and XSL content (`1.3.4`, `1.3.5`), SSRF allowlists of protocols, domains, paths and ports (`1.3.6`), template injection (`1.3.7`), JNDI (`1.3.8`), memcache (`1.3.9`), format strings (`1.3.10`), SMTP and IMAP (`1.3.11`). L3: ReDoS (`1.3.12`).         |
| V1.4 Memory, String, and Unmanaged Code     | L2: memory-safe strings and copies (`1.4.1`), integer overflow (`1.4.2`), use-after-free (`1.4.3`).                                                                                                                                                                                                                                                                                                                                |
| V1.5 Safe Deserialization                   | `v5.0.0-1.5.1` (L1) restrictive XML parser configuration, no external entities (XXE). `v5.0.0-1.5.2` (L2) allowlist object types when deserializing untrusted data. `v5.0.0-1.5.3` (L3) consistent parsing across parsers of the same data type.                                                                                                                                                                                   |

## V2 Validation and Business Logic

13 requirements: 4 L1, 7 L2, 2 L3. Input matches business expectations, flows run in order, limits stop automated abuse, and high-value flows consider abuse cases (V2 Control Objective).

| Section                                          | Key requirements                                                                                                                                                                                                                                                                                                                 |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| V2.1 Validation and Business Logic Documentation | `v5.0.0-2.1.1` (L1) document input validation rules. `v5.0.0-2.1.2` (L2) document consistency rules for combined items. `v5.0.0-2.1.3` (L2) document per-user and global business limits.                                                                                                                                        |
| V2.2 Input Validation                            | `v5.0.0-2.2.1` (L1) validate input against business expectations by allowlist or expected structure; L1 may focus on input used for business or security decisions, L2 and up on all input. `v5.0.0-2.2.2` (L1) enforce validation at a trusted service layer. `v5.0.0-2.2.3` (L2) combinations of related items are reasonable. |
| V2.3 Business Logic Security                     | `v5.0.0-2.3.1` (L1) steps of a flow run in order without skipping. L2: enforce documented limits (`2.3.2`), transactions all-or-nothing (`2.3.3`), locking for limited resources (`2.3.4`). L3: multi-user approval for high-value flows (`2.3.5`).                                                                              |
| V2.4 Anti-automation                             | `v5.0.0-2.4.1` (L2) anti-automation against excessive calls (exfiltration, quota exhaustion, denial of service, costly resources). `v5.0.0-2.4.2` (L3) realistic human timing.                                                                                                                                                   |

## V3 Web Frontend Security

31 requirements: 8 L1, 11 L2, 12 L3. Attacks through a web frontend; does not apply to machine-to-machine solutions (V3 Control Objective).

| Section                                    | Key requirements                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| V3.1 Web Frontend Security Documentation   | `v5.0.0-3.1.1` (L3) document the browser security features the application needs.                                                                                                                                                                                                                                                                                                                                                                                  |
| V3.2 Unintended Content Interpretation     | `v5.0.0-3.2.1` (L1) prevent rendering content in the wrong context. `v5.0.0-3.2.2` (L1) render text with safe functions such as `createTextNode`. `v5.0.0-3.2.3` (L3) DOM clobbering.                                                                                                                                                                                                                                                                              |
| V3.3 Cookie Setup                          | `v5.0.0-3.3.1` (L1) `Secure` attribute, and the `__Secure-` prefix when `__Host-` is not used. L2: `SameSite` by purpose (`3.3.2`), `__Host-` unless shared (`3.3.3`), `HttpOnly` for values scripts do not need (`3.3.4`). L3: name and value at most 4096 bytes (`3.3.5`).                                                                                                                                                                                       |
| V3.4 Browser Security Mechanism Headers    | `v5.0.0-3.4.1` (L1) HSTS on all responses, max-age at least 1 year, subdomains from L2. `v5.0.0-3.4.2` (L1) fixed or allowlisted `Access-Control-Allow-Origin`. L2: CSP with at least `object-src 'none'` and `base-uri 'none'` and an allowlist, nonces or hashes (`3.4.3`, per-response nonces or hashes at L3), `nosniff` (`3.4.4`), Referrer-Policy (`3.4.5`), `frame-ancestors` (`3.4.6`). L3: CSP reporting (`3.4.7`), Cross-Origin-Opener-Policy (`3.4.8`). |
| V3.5 Browser Origin Separation             | `v5.0.0-3.5.1` and `v5.0.0-3.5.2` (L1) CSRF defense, with or without reliance on CORS preflight. `v5.0.0-3.5.3` (L1) sensitive functions use non-safe methods, or strict `Sec-Fetch-*` validation. L2: separate hostnames per application (`3.5.4`), `postMessage` origin checks (`3.5.5`). L3: no JSONP (`3.5.6`), no authorized data in scripts (`3.5.7`), authenticated resources only embedded when intended (`3.5.8`).                                        |
| V3.6 External Resource Integrity           | `v5.0.0-3.6.1` (L3) external assets only if static, versioned and protected with Subresource Integrity.                                                                                                                                                                                                                                                                                                                                                            |
| V3.7 Other Browser Security Considerations | L2: only supported client-side technologies (`3.7.1`), redirects to foreign hosts only when allowlisted (`3.7.2`). L3: warn before leaving (`3.7.3`), HSTS preload (`3.7.4`), documented behavior for browsers lacking features (`3.7.5`).                                                                                                                                                                                                                         |

## V4 API and Web Service

16 requirements: 2 L1, 8 L2, 6 L3. APIs used by browsers or other consumers (JSON, XML, GraphQL). Authentication, session and validation chapters also apply to APIs; this chapter is not tested in isolation (V4 Control Objective).

| Section                                | Key requirements                                                                                                                                                                                                                                                                                                                       |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| V4.1 Generic Web Service Security      | `v5.0.0-4.1.1` (L1) `Content-Type` with charset matches the body. L2: only user-facing endpoints redirect HTTP to HTTPS (`4.1.2`); intermediary-set headers such as `X-Forwarded-*` cannot be overridden by users (`4.1.3`). L3: only supported methods (`4.1.4`), per-message signatures for highly sensitive transactions (`4.1.5`). |
| V4.2 HTTP Message Structure Validation | `v5.0.0-4.2.1` (L2) all components agree on message boundaries to prevent request smuggling. L3: consistent `Content-Length` (`4.2.2`), no connection-specific headers in HTTP/2 and HTTP/3 (`4.2.3`), no CR or LF in HTTP/2 and HTTP/3 headers (`4.2.4`), safe outbound request building (`4.2.5`).                                   |
| V4.3 GraphQL                           | L2: query allowlist, depth or cost limits (`4.3.1`); introspection off in production unless public (`4.3.2`).                                                                                                                                                                                                                          |
| V4.4 WebSocket                         | `v5.0.0-4.4.1` (L1) WSS only. L2: `Origin` check at handshake (`4.4.2`), dedicated tokens when normal sessions cannot be used (`4.4.3`), obtained through the authenticated HTTPS session (`4.4.4`).                                                                                                                                   |

## V5 File Handling

13 requirements: 4 L1, 5 L2, 4 L3. Denial of service, unauthorized access and storage exhaustion through files (V5 Control Objective).

| Section                          | Key requirements                                                                                                                                                                                                                                                                                                                                                    |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| V5.1 File Handling Documentation | `v5.0.0-5.1.1` (L2) document permitted types, extensions and maximum sizes (including unpacked) per upload feature.                                                                                                                                                                                                                                                 |
| V5.2 File Upload and Content     | `v5.0.0-5.2.1` (L1) size limits the application can process. `v5.0.0-5.2.2` (L1) extension matches expected types and content matches the extension (magic bytes, re-writing); all files from L2. L2: archive limits on uncompressed size and file count (`5.2.3`). L3: per-user quotas (`5.2.4`), no symlinks in archives (`5.2.5`), pixel flood limits (`5.2.6`). |
| V5.3 File Storage                | `v5.0.0-5.3.1` (L1) uploaded files in public folders are never executed. `v5.0.0-5.3.2` (L1) server-generated paths, or strict validation, against path traversal, LFI, RFI and SSRF. `v5.0.0-5.3.3` (L3) ignore archive path information (zip slip).                                                                                                               |
| V5.4 File Download               | L2: validate or ignore user-submitted names and set `Content-Disposition` (`5.4.1`), encode served file names (`5.4.2`), scan untrusted files with antivirus (`5.4.3`).                                                                                                                                                                                             |

## V6 Authentication

47 requirements: 13 L1, 22 L2, 12 L3. Based in large part on NIST SP 800-63B but focused on common threats; it does not cover every point of that standard, and full NIST compliance requires NIST SP 800-63 itself. Adaptive, risk-based authentication is in V8 (V6 Control Objective).

| Section                                               | Key requirements                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| V6.1 Authentication Documentation                     | `v5.0.0-6.1.1` (L1) document rate limiting, anti-automation and adaptive response against credential stuffing and brute force, without enabling malicious lockout. L2: context-specific banned words (`6.1.2`), all authentication pathways (`6.1.3`).                                                                                                                                                                                                                                        |
| V6.2 Password Security                                | L1: at least 8 characters, 15 strongly recommended (`6.2.1`); users can change passwords (`6.2.2`) with the current one (`6.2.3`); check against at least the top 3000 passwords (`6.2.4`); no composition rules (`6.2.5`); masked input (`6.2.6`); paste and password managers allowed (`6.2.7`); no truncation or case change (`6.2.8`). L2: at least 64 characters allowed (`6.2.9`), no periodic rotation (`6.2.10`), context words (`6.2.11`) and breached passwords (`6.2.12`) blocked. |
| V6.3 General Authentication Security                  | `v5.0.0-6.3.1` (L1) controls against credential stuffing and brute force. `v5.0.0-6.3.2` (L1) no default accounts. `v5.0.0-6.3.3` (L2) multi-factor authentication or a combination of single-factor mechanisms; at L3 one factor is hardware-based, phishing-resistant and needs a user action. L3: notify on suspicious attempts (`6.3.5`), email is not an authentication factor (`6.3.6`), notify after credential changes (`6.3.7`), no user enumeration (`6.3.8`).                      |
| V6.4 Authentication Factor Lifecycle and Recovery     | L1: random, short-lived initial passwords and activation codes (`6.4.1`); no password hints or secret questions (`6.4.2`). L2: reset does not bypass MFA (`6.4.3`); lost factor needs identity proofing at enrollment level (`6.4.4`).                                                                                                                                                                                                                                                        |
| V6.5 General Multi-factor authentication requirements | L2: lookup secrets, out-of-band codes and TOTPs single-use (`6.5.1`), salted hashing of low-entropy lookup secrets (`6.5.2`), CSPRNG generation (`6.5.3`), at least 20 bits of entropy (`6.5.4`), defined lifetimes (`6.5.5`). L3: revocable factors (`6.5.6`), biometrics only as a second factor (`6.5.7`), trusted TOTP time source (`6.5.8`).                                                                                                                                             |
| V6.6 Out-of-Band authentication mechanisms            | `v5.0.0-6.6.1` (L2) SMS or phone OTP only for a validated number, with a stronger alternative and risk information; not offered at L3. L2: bound to the original request (`6.6.2`), rate limited (`6.6.3`). L3: push-bombing limits (`6.6.4`).                                                                                                                                                                                                                                                |
| V6.7 Cryptographic authentication mechanism           | L3: protect verification certificates (`6.7.1`), challenge nonce at least 64 bits (`6.7.2`).                                                                                                                                                                                                                                                                                                                                                                                                  |
| V6.8 Authentication with an Identity Provider         | L2: no identity spoofing across IdPs (`6.8.1`), always validate assertion signatures (`6.8.2`), SAML assertions used once (`6.8.3`), check `acr`, `amr` and `auth_time` or assume the weakest method (`6.8.4`).                                                                                                                                                                                                                                                                               |

## V7 Session Management

19 requirements: 6 L1, 12 L2, 1 L3. Sessions are unique, unguessable and unshared, and are invalidated and timed out. Cookie rules are in V3; self-contained token rules are in V9 (V7 Control Objective).

| Section                                      | Key requirements                                                                                                                                                                                                                                                                                                                                        |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| V7.1 Session Management Documentation        | L2: document inactivity timeout and absolute lifetime (`7.1.1`), concurrent sessions (`7.1.2`), federated session systems (`7.1.3`).                                                                                                                                                                                                                    |
| V7.2 Fundamental Session Management Security | L1: verify tokens at a trusted backend (`7.2.1`); dynamic, not static, tokens (`7.2.2`); reference tokens unique and from a CSPRNG (`7.2.3`); new token on authentication and re-authentication (`7.2.4`).                                                                                                                                              |
| V7.3 Session Timeout                         | L2: inactivity timeout (`7.3.1`) and absolute lifetime (`7.3.2`) per the documented decisions.                                                                                                                                                                                                                                                          |
| V7.4 Session Termination                     | `v5.0.0-7.4.1` (L1) terminated sessions cannot be reused; self-contained tokens need a deny list, a per-user cut-off time or per-user key rotation. `v5.0.0-7.4.2` (L1) end all sessions when an account is disabled or deleted. L2: offer to end other sessions after factor changes (`7.4.3`), visible logout (`7.4.4`), admin termination (`7.4.5`). |
| V7.5 Defenses Against Session Abuse          | L2: re-authenticate before changing sensitive account attributes (`7.5.1`), users can view and end sessions (`7.5.2`). L3: step-up for highly sensitive transactions (`7.5.3`).                                                                                                                                                                         |
| V7.6 Federated Re-authentication             | L2: RP and IdP session lifetimes behave as documented (`7.6.1`); new sessions need consent or explicit action (`7.6.2`).                                                                                                                                                                                                                                |

## V8 Authorization

13 requirements: 4 L1, 3 L2, 6 L3. Least privilege: document the rules, and give consumers access only to what their entitlements allow (V8 Control Objective).

| Section                                 | Key requirements                                                                                                                                                                                                                                                         |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| V8.1 Authorization Documentation        | `v5.0.0-8.1.1` (L1) document function-level and data-specific rules. `v5.0.0-8.1.2` (L2) field-level rules. L3: environmental and contextual attributes (`8.1.3`, `8.1.4`).                                                                                              |
| V8.2 General Authorization Design       | `v5.0.0-8.2.1` (L1) function-level access needs explicit permission. `v5.0.0-8.2.2` (L1) data-specific access needs explicit permission, against IDOR and BOLA. `v5.0.0-8.2.3` (L2) field-level access, against BOPLA. `v5.0.0-8.2.4` (L3) adaptive controls on context. |
| V8.3 Operation Level Authorization      | `v5.0.0-8.3.1` (L1) enforce at a trusted service layer, never in client-side code. L3: apply changes to authorization data immediately or alert and revert (`8.3.2`); decide on the originating subject's permissions, not an intermediary's (`8.3.3`).                  |
| V8.4 Other Authorization Considerations | `v5.0.0-8.4.1` (L2) cross-tenant controls in multi-tenant applications. `v5.0.0-8.4.2` (L3) layered security for administrative interfaces.                                                                                                                              |
