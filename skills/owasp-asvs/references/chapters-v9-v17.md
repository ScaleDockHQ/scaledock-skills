# Chapters V9 to V17

Read this when scoping, implementing or verifying the token, OAuth and OIDC, cryptography, communication, configuration, data protection, secure coding, logging and WebRTC chapters of ASVS 5.0.0, or when you need the cryptography appendix. Each chapter lists its sections, its requirement count by level (from the 5.0.0 flat JSON), and its key requirements, paraphrased. Copy the full requirement text from the official JSON or markdown into any requirement list, report or contract. Sources: the 5.0.0 chapter files `0x18` to `0x26`, Appendix C and D, and the flat JSON, listed in [Sources](../SKILL.md#sources).

## V9 Self-contained Tokens

7 requirements: 4 L1, 3 L2. Tokens whose claims a receiving service relies on, such as JWTs and SAML assertions, as opposed to reference tokens looked up locally (V9 Control Objective).

| Section                         | Key requirements                                                                                                                                                                                                                                                                                                                                 |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| V9.1 Token source and integrity | L1: validate the signature or MAC before using the content (`9.1.1`); allowlist algorithms per context, never `none`, ideally only symmetric or only asymmetric, with extra controls against key confusion if both (`9.1.2`); keys only from trusted pre-configured sources, with `jku`, `x5u` and `jwk` checked against an allowlist (`9.1.3`). |
| V9.2 Token content              | `v5.0.0-9.2.1` (L1) check the validity period (`nbf`, `exp`). L2: check the token type and purpose, for example only access tokens for authorization and only ID Tokens for authentication (`9.2.2`); check the audience against an allowlist (`9.2.3`); issuers that share a key across audiences must restrict the audience (`9.2.4`).         |

## V10 OAuth and OIDC

36 requirements: 5 L1, 24 L2, 7 L3. OAuth for delegated authorization and OpenID Connect for identity on top of it; OAuth requirements also apply to OIDC. Pick the sections for the roles the application plays (V10 Control Objective).

| Section                               | Key requirements                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| V10.1 Generic OAuth and OIDC Security | L2: send tokens only to components that need them, for example only the backend in a backend-for-frontend (`10.1.1`); accept values only from a flow started by the same user agent session, with unguessable, transaction-specific `code_verifier`, `state` or `nonce` (`10.1.2`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| V10.2 OAuth Client                    | L2: CSRF protection on the code flow through PKCE or `state` (`10.2.1`); mix-up defense when talking to several authorization servers, for example validating `iss` (`10.2.2`). L3: request only needed scopes (`10.2.3`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| V10.3 OAuth Resource Server           | L2: accept only tokens for this audience (`aud` or introspection) (`10.3.1`); decide on `sub`, `scope` and `authorization_details` (`10.3.2`); identify users by non-reassignable claims, typically `iss` plus `sub` (`10.3.3`); check authentication strength or recentness (`10.3.4`). L3: sender-constrained tokens through mTLS or DPoP (`10.3.5`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| V10.4 OAuth Authorization Server      | L1: exact-match redirect URI allowlist per client (`10.4.1`); single-use codes (`10.4.2`); short-lived codes, up to 10 minutes at L1 and L2 and 1 minute at L3 (`10.4.3`); only the grants a client needs, never `token` (implicit) or `password` (`10.4.4`); refresh token replay protection for public clients through sender-constraining or rotation with family revocation (`10.4.5`). L2: PKCE required, no `plain` (`10.4.6`); safeguards for unauthenticated dynamic registration (`10.4.7`); absolute refresh token expiry (`10.4.8`); user revocation (`10.4.9`); confidential client authentication on back-channel requests (`10.4.10`); only required scopes assigned (`10.4.11`). L3: restricted `response_mode` (`10.4.12`), PAR with every code grant (`10.4.13`), only sender-constrained access tokens (`10.4.14`), untampered `authorization_details` (`10.4.15`), confidential clients with mTLS or `private_key_jwt` (`10.4.16`). |
| V10.5 OIDC Client                     | L2: ID Token replay defense through `nonce` (`10.5.1`); identify users by `sub` (`10.5.2`); reject metadata whose issuer does not exactly match the configured one (`10.5.3`); check `aud` is the client (`10.5.4`); back-channel logout token typed `logout+jwt` with the right `event` claim and no `nonce` (`10.5.5`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| V10.6 OpenID Provider                 | L2: only `code`, `ciba`, `id_token` or `id_token code` response modes, preferring `code`, never `token` (`10.6.1`); forced-logout defense through user confirmation or `id_token_hint` (`10.6.2`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| V10.7 Consent Management              | L2: consent per authorization request, always prompting when the client's identity is not assured (`10.7.1`); clear consent information (`10.7.2`); users can review, modify and revoke consents (`10.7.3`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |

## V11 Cryptography

24 requirements: 3 L1, 11 L2, 10 L3. Robust, agile cryptography and key management. "Approved" algorithms and parameters are defined in Appendix C. Cryptography used to solve another problem (secrets, transport) is in other chapters (V11 Control Objective).

| Section                                         | Key requirements                                                                                                                                                                                                                                                                                                          |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| V11.1 Cryptographic Inventory and Documentation | L2: documented key management policy and lifecycle (`11.1.1`); maintained cryptographic inventory of keys, algorithms and certificates (`11.1.2`). L3: discovery mechanisms (`11.1.3`); a migration plan, for example to post-quantum cryptography (`11.1.4`).                                                            |
| V11.2 Secure Cryptography Implementation        | L2: industry-validated implementations (`11.2.1`); crypto agility, including replacing keys and re-encrypting data (`11.2.2`); at least 128 bits of security, for example 256-bit ECC or 3072-bit RSA (`11.2.3`). L3: constant-time operations (`11.2.4`); fail securely, for example against padding oracles (`11.2.5`). |
| V11.3 Encryption Algorithms                     | L1: no ECB or PKCS#1 v1.5 padding (`11.3.1`); only approved ciphers and modes such as AES-GCM (`11.3.2`). L2: authenticated encryption (`11.3.3`). L3: no nonce or IV reuse per key (`11.3.4`); encrypt-then-MAC (`11.3.5`).                                                                                              |
| V11.4 Hashing and Hash-based Functions          | `v5.0.0-11.4.1` (L1) only approved hash functions; MD5 never for cryptography. L2: passwords stored with an approved, computationally intensive KDF (`11.4.2`); collision-resistant hashes for signatures and integrity (`11.4.3`); approved KDFs with stretching for password-derived keys (`11.4.4`).                   |
| V11.5 Random Values                             | `v5.0.0-11.5.1` (L2) CSPRNG with at least 128 bits of entropy for non-guessable values; UUIDs do not qualify. `v5.0.0-11.5.2` (L3) secure under heavy demand.                                                                                                                                                             |
| V11.6 Public Key Cryptography                   | L2: approved algorithms for key generation and signatures (`11.6.1`). L3: approved key exchange with secure parameters (`11.6.2`).                                                                                                                                                                                        |
| V11.7 In-Use Data Cryptography                  | L3: full memory encryption (`11.7.1`); data minimization and encryption right after use (`11.7.2`).                                                                                                                                                                                                                       |

### Appendix C: Cryptography Standards

Appendix C marks each mechanism Approved (A, usable), Legacy (L, compatibility only, replace as soon as possible) or Disallowed (D, must not be used) (Appendix C, introduction). For password storage the 5.0.0 table approves argon2id (for example `t = 2, m ≥ 19456 (19 MiB), p = 1`), scrypt, bcrypt (cost at least 10), PBKDF2-HMAC-SHA-512 (at least 210,000 iterations) and PBKDF2-HMAC-SHA-256 (at least 600,000), and lists PBKDF2-HMAC-SHA-1 (at least 1,300,000) as legacy (Appendix C, Hash Functions for Password Storage). The bleeding edge has edited these tables; use the 5.0.0 text for a 5.0.0 verification.

## V12 Secure Communication

12 requirements: 3 L1, 6 L2, 3 L3. Data in transit between users and services and between internal services (V12 Control Objective).

| Section                                                 | Key requirements                                                                                                                                                                                                                                                                                                                               |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| V12.1 General TLS Security Guidance                     | `v5.0.0-12.1.1` (L1) only recent TLS versions such as 1.2 and 1.3, preferring the latest. L2: recommended cipher suites, forward secrecy only at L3 (`12.1.2`); trust checks on mTLS client certificates (`12.1.3`). L3: revocation checking such as OCSP stapling (`12.1.4`); Encrypted Client Hello (`12.1.5`).                              |
| V12.2 HTTPS Communication with External Facing Services | L1: TLS for all external HTTP services with no fallback (`12.2.1`); publicly trusted certificates (`12.2.2`).                                                                                                                                                                                                                                  |
| V12.3 General Service to Service Communication Security | L2: encrypted protocols for all inbound and outbound connections (`12.3.1`); TLS clients validate certificates (`12.3.2`); TLS between internal HTTP services (`12.3.3`); internal certificates trusted only through specific internal CAs or pinned self-signed certificates (`12.3.4`). L3: strong mutual service authentication (`12.3.5`). |

## V13 Configuration

21 requirements: 1 L1, 12 L2, 8 L3. The default configuration must be secure for the Internet: leakage, component communication and secrets (V13 Control Objective).

| Section                                   | Key requirements                                                                                                                                                                                                                                                                                                                  |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| V13.1 Configuration Documentation         | L2: document all communication needs, including user-supplied destinations (`13.1.1`). L3: connection limits (`13.1.2`), resource-management strategies (`13.1.3`), critical secrets and their rotation schedule (`13.1.4`).                                                                                                      |
| V13.2 Backend Communication Configuration | L2: authenticate backend components with individual service accounts, short-term tokens or certificates, not static passwords or API keys (`13.2.1`); least privilege (`13.2.2`); no default credentials (`13.2.3`); outbound allowlists (`13.2.4`, `13.2.5`). L3: follow the documented per-connection configuration (`13.2.6`). |
| V13.3 Secret Management                   | `v5.0.0-13.3.1` (L2) a secrets management solution such as a vault; no secrets in source or build artifacts; hardware-backed at L3. `v5.0.0-13.3.2` (L2) least privilege on secrets. L3: cryptographic operations in an isolated module (`13.3.3`); expiring, rotated secrets (`13.3.4`).                                         |
| V13.4 Unintended Information Leakage      | `v5.0.0-13.4.1` (L1) no reachable `.git` or `.svn` metadata. L2: debug off in production (`13.4.2`), no directory listings (`13.4.3`), no TRACE (`13.4.4`), no exposed internal documentation or monitoring endpoints (`13.4.5`). L3: no detailed backend versions (`13.4.6`); serve only expected file extensions (`13.4.7`).    |

## V14 Data Protection

13 requirements: 2 L1, 7 L2, 4 L3. Define what data needs protection and how. Detecting bulk extraction is in V16 and setting limits is in V2 (V14 Control Objective).

| Section                             | Key requirements                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| V14.1 Data Protection Documentation | L2: identify and classify sensitive data into protection levels (`14.1.1`); document protection requirements per level, covering encryption, integrity, retention, logging and privacy (`14.1.2`).                                                                                                                                                                                                                                          |
| V14.2 General Data Protection       | `v5.0.0-14.2.1` (L1) sensitive data only in the body or headers, never the URL or query string. L2: not cached in server components (`14.2.2`); not sent to untrusted parties such as trackers (`14.2.3`); controls per the documented levels (`14.2.4`). L3: caches only for expected content types (`14.2.5`); minimal data returned (`14.2.6`); retention with automatic deletion (`14.2.7`); metadata stripped from uploads (`14.2.8`). |
| V14.3 Client-side Data Protection   | `v5.0.0-14.3.1` (L1) clear authenticated data from client storage when the session ends; `Clear-Site-Data` may help. L2: `Cache-Control: no-store` for sensitive data (`14.3.2`); no sensitive data in browser storage except session tokens (`14.3.3`).                                                                                                                                                                                    |

## V15 Secure Coding and Architecture

21 requirements: 3 L1, 10 L2, 8 L3. General design and coding requirements that do not belong to one functional area (V15 Control Objective).

| Section                                            | Key requirements                                                                                                                                                                                                                                                                                                                                                       |
| -------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| V15.1 Secure Coding and Architecture Documentation | `v5.0.0-15.1.1` (L1) documented risk-based remediation time frames for vulnerable components and library updates. L2: an SBOM from trusted repositories (`15.1.2`); document resource-heavy functionality and its availability defenses (`15.1.3`). L3: flag risky components (`15.1.4`) and dangerous functionality (`15.1.5`).                                       |
| V15.2 Security Architecture and Dependencies       | `v5.0.0-15.2.1` (L1) no component past its documented remediation time frame. L2: availability defenses for resource-heavy functions (`15.2.2`); no test code or samples in production (`15.2.3`). L3: dependencies from the expected repository, no dependency confusion (`15.2.4`); extra protection around dangerous functionality (`15.2.5`).                      |
| V15.3 Defensive Coding                             | `v5.0.0-15.3.1` (L1) return only the required fields of a data object. L2: backend calls do not follow redirects unless intended (`15.3.2`); mass assignment defense (`15.3.3`); trusted client IP propagation (`15.3.4`); strict types and comparisons (`15.3.5`); prototype pollution defense in JavaScript (`15.3.6`); HTTP parameter pollution defense (`15.3.7`). |
| V15.4 Safe Concurrency                             | L3: thread-safe shared objects (`15.4.1`), atomic check-then-act against TOCTOU (`15.4.2`), deadlock-free locking (`15.4.3`), no thread starvation (`15.4.4`).                                                                                                                                                                                                         |

## V16 Security Logging and Error Handling

17 requirements: 0 L1, 16 L2, 1 L3. Security logs record authentication and access decisions and bypass attempts for detection and response; they must not leak sensitive data, and the application must fail securely (V16 Control Objective).

| Section                              | Key requirements                                                                                                                                                                                                                                                                 |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| V16.1 Security Logging Documentation | `v5.0.0-16.1.1` (L2) a log inventory per layer: events, formats, storage, use, access and retention.                                                                                                                                                                             |
| V16.2 General Logging                | L2: when, where, who and what in each entry (`16.2.1`); synchronized clocks and UTC or explicit offsets (`16.2.2`); logs only to inventoried destinations (`16.2.3`); a format the log processor can read (`16.2.4`); sensitive data logged per its protection level (`16.2.5`). |
| V16.3 Security Events                | L2: all authentication attempts (`16.3.1`); failed authorization, and all authorization decisions at L3 (`16.3.2`); documented security events and bypass attempts (`16.3.3`); unexpected errors and control failures (`16.3.4`).                                                |
| V16.4 Log Protection                 | L2: encode to prevent log injection (`16.4.1`); protect from access and modification (`16.4.2`); ship to a logically separate system (`16.4.3`).                                                                                                                                 |
| V16.5 Error Handling                 | L2: generic error messages without stack traces, queries, keys or tokens (`16.5.1`); keep operating securely when external resources fail (`16.5.2`); fail closed (`16.5.3`). L3: a last-resort handler for unhandled exceptions (`16.5.4`).                                     |

## Appendix D: Recommendations

Items considered for 5.0 but not made requirements, either in scope but not mandatory (for example a password strength meter, `security.txt`, client-side validation in addition to server-side, GraphQL authorization in the business logic layer) or software security principles that used to be 4.0 requirements (Appendix D). They do not count toward a level.
