# DID resolution and DID URL dereferencing

Read this when building or calling a DID resolver or DID URL dereferencer, mapping its errors, exposing it over HTTP, or reasoning about whether a resolution result can be trusted. Sources: DID Resolution 1.0 (Candidate Recommendation Draft, 1 October 2026) and DID 1.0 § 7, listed in [Sources](../SKILL.md#sources). "Resolution § x" means DID Resolution 1.0. Sections 5, 6, 8 and 10 of DID Resolution are marked "Feature at Risk" and may change heavily or be removed.

## The resolve function

DID Resolution § 4:

```text
resolve(did, resolutionOptions) → « didResolutionMetadata, didDocument, didDocumentMetadata »
```

- Every conforming resolver MUST implement `resolve` for at least one DID method and MUST be able to return a DID document. It does not alter this signature, though it may expose other functions.
- `did` is REQUIRED and MUST be a conformant DID. `resolutionOptions` is REQUIRED but MAY be empty.
- `didResolutionMetadata` is REQUIRED. On error it MUST NOT be empty and MUST contain an `error` property.
- On success, `didDocument` MUST be a DID document in a conformant representation, and its `id` MUST be string-equal to the resolved DID. On failure it MUST be empty.
- On success, `didDocumentMetadata` MUST be a metadata structure. On failure it MUST be an empty metadata structure.

### DID 1.0 § 7.1 for comparison

DID 1.0 defined two functions: `resolve` returns the document in the abstract data model, and `resolveRepresentation(did, resolutionOptions) → « didResolutionMetadata, didDocumentStream, didDocumentMetadata »` returns a byte stream. In DID 1.0 the `accept` option MUST NOT be used with `resolve`, `contentType` is REQUIRED for `resolveRepresentation` and MUST NOT be present for `resolve`, and errors are keyword strings: `invalidDid`, `notFound`, `representationNotSupported` (DID 1.0 § 7.1.1, § 7.1.2). DID Resolution 1.0 removed `resolveRepresentation` (Resolution App. C).

## Resolution options (Resolution § 4.1, § 13.2)

| Option               | Value and effect                                                                                                                                |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `accept`             | The caller's preferred representation, expressed as an HTTP `Accept` header value (RFC 9110 § 12.5.1). The resolver SHOULD use it if supported. |
| `expandRelativeUrls` | Boolean. When `true`, the resolver expands relative DID URLs in the document to absolute DID URLs.                                              |
| `versionId`          | As the DID parameter (Resolution § 3).                                                                                                          |
| `versionTime`        | As the DID parameter (Resolution § 3). Mutually exclusive with `versionId` (§ 13.4).                                                            |
| `noCache`            | `"false"` (default) allows caching; `"true"` requests a fresh document from the verifiable data registry. OPTIONAL (§ 13.2).                    |

Other options SHOULD be registered in the DID Resolution Extensions note (Resolution § 4.1).

## Metadata

### Resolution metadata (Resolution § 4.2)

Data about the resolution process, sourced from the resolver; it typically changes between calls.

- `contentType` (OPTIONAL): an ASCII media type string of the returned document. If present, the caller MUST use it to decide how to parse and process `didDocument`.
- `error`: an RFC 9457 problem details object (see [Errors](#errors)).
- `proof` (MAY): a set of maps, each a proof generated by the resolver; method-independent.
- Other examples: duration, caching information, and network information about the verifiable data registry used.

### Document metadata (Resolution § 4.3, DID 1.0 § 7.1.3)

Data about the DID document, from the controller or the DID method. Metadata attested by the controller has no inherent guarantee of accuracy, so be careful when business logic relies on it (Resolution § 4.3).

| Property        | Rule                                                                                                                                                      |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `created`       | SHOULD be present: timestamp of the Create operation, in the § 3.1 datetime format.                                                                       |
| `updated`       | SHOULD be present: timestamp of the last Update for the resolved version; omitted if never updated; may equal `created` if they differ by under a second. |
| `deactivated`   | MUST be `true` if the DID is deactivated. Otherwise OPTIONAL, and if present MUST be `false`.                                                             |
| `nextUpdate`    | MAY be present if the resolved version is not the latest: timestamp of the next Update.                                                                   |
| `versionId`     | SHOULD be present: ASCII string, the version of the last Update for the resolved version.                                                                 |
| `nextVersionId` | MAY be present if the resolved version is not the latest: version of the next Update.                                                                     |
| `equivalentId`  | MAY: a set of DIDs logically equivalent to `id`, produced by the same method. The method MUST guarantee equivalence. Retain all values.                   |
| `canonicalId`   | MAY: a single equivalent DID that is canonical for the subject. The method MUST guarantee equivalence. Use it as the primary ID.                          |
| `proof`         | MAY (Resolution only): a set of method-specific proofs.                                                                                                   |

`equivalentId` and `canonicalId` are a much stronger form of equivalence than `alsoKnownAs`, because the method guarantees them (Resolution § 4.3 note).

### Metadata structure (Resolution § 7, DID 1.0 § 7.3)

Metadata structures are maps whose values are strings, maps, lists, sets, booleans or null (DID 1.0 § 7.3); DID Resolution also allows numbers, with guidance to avoid floating-point values and values above \(2^{32}-1\) for interoperability (Resolution § 7). They need to be serializable to JSON: all `dereference` inputs and outputs apart from `contentStream` MUST be (Resolution § 5).

## Resolution algorithm (Resolution § 4.4)

Run the checks in this order. Each failure returns the error, `didDocument: null` and empty document metadata.

1. The DID does not match the `did` ABNF: `INVALID_DID`.
2. The DID method is not supported: `METHOD_NOT_SUPPORTED`.
3. An option is not supported: `FEATURE_NOT_SUPPORTED`.
4. An option is invalid: `INVALID_OPTIONS`.
5. Run the method's Resolve operation:
   - The DID does not exist: `NOT_FOUND`.
   - The DID is deactivated: `didDocument: null` and `didDocumentMetadata` containing `"deactivated": true`. This is not an error.
   - Otherwise the result is the output DID document, which MUST be in a conformant representation.
6. If `expandRelativeUrls` is `true`, expand relative DID URLs in service, verification method, verification relationship and extension property values using the Relative DID URLs rules (DID 1.0 § 3.2.2).
7. Return the document with its metadata. The algorithm text places `contentType` in `didDocumentMetadata` here, while § 4.2 defines it as resolution metadata; follow § 4.2 and the HTTP binding, which read it from `didResolutionMetadata`.

Any unexpected failure returns `INTERNAL_ERROR`.

## Resolution result (Resolution § 9)

The JSON form of a resolution result has media type `application/did-resolution` and the top-level keys `didDocument`, `didResolutionMetadata` and `didDocumentMetadata`:

```json
{
  "didDocument": {
    "@context": "https://www.w3.org/ns/did/v1.1",
    "id": "did:example:123456789abcdefghi"
  },
  "didResolutionMetadata": { "contentType": "application/did" },
  "didDocumentMetadata": {
    "created": "2019-03-23T06:35:22Z",
    "updated": "2023-08-10T13:40:06Z"
  }
}
```

Failure:

```json
{
  "didDocument": null,
  "didResolutionMetadata": {
    "error": {
      "type": "https://www.w3.org/ns/did#NOT_FOUND",
      "title": "DID not found",
      "detail": "The DID did:example:123 does not exist in the registry."
    }
  },
  "didDocumentMetadata": {}
}
```

## DID URL dereferencing (Resolution § 5, at risk)

```text
dereference(didUrl, dereferenceOptions) → « dereferencingMetadata, contentStream, contentMetadata »
```

- Every conforming dereferencer MUST implement it for at least one DID method. To dereference a fragment, the complete DID URL including the fragment MUST be passed (Resolution § 5).
- `dereferencingMetadata` is REQUIRED, and on error MUST NOT be empty and MUST contain `error`. On success it SHOULD carry `contentType` (§ 5.2).
- `contentStream` holds the resource on success and MUST be empty on failure. `contentMetadata` is a metadata structure on success (DID document metadata if the content is a DID document) and empty on failure (§ 5).
- Options: `accept` (HTTP Accept syntax) and `verificationRelationship` (ASCII string). With `verificationRelationship`, an error MUST be raised if the URL does not dereference to a verification method authorized for that relationship (§ 5.1).

### Dereferencing the resource (§ 5.4.1)

1. The DID URL does not match `did-url`: `INVALID_DID_URL`.
2. Resolve the DID with § 4. All dereferencing options and all DID parameters of the DID URL MUST be passed as resolution options. A DID that does not exist: `NOT_FOUND`.
3. Remove the fragment and continue with the rest.
4. No path and no query: return the resolved DID document and its metadata.
5. A `service` and/or `serviceType` parameter, optionally with `relativeRef`:
   - Select the services whose `id` matches `service` (resolve relative references to absolute ones before comparing, per RFC 3986 § 5 and Relative DID URLs) and/or whose `type` matches `serviceType`.
   - With `relativeRef`: skip services whose `serviceEndpoint` is a map; collect string endpoints, including the strings in a set; resolve `relativeRef` against each with RFC 3986 § 5 reference resolution.
   - `accept` missing or a DID document media type: return the DID document with only the selected services.
   - `accept` is `text/uri-list`: return the selected service endpoint URLs, with `contentType` `text/uri-list`.
   - Any other `accept`: `REPRESENTATION_NOT_SUPPORTED`.
6. Any other path or query: the DID method, an extension specification or the client MAY define how to dereference it. Otherwise `NOT_FOUND`.

### Dereferencing the fragment (§ 5.4.2)

- The resource is a DID document and `verificationRelationship` is set: dereference the fragment to a verification method; raise `INVALID_VERIFICATION_METHOD` if it is not conforming, and `INVALID_RELATIONSHIP_FOR_VERIFICATION_METHOD` if it is not in that relationship.
- The resource is a selected service endpoint URL: raise an error if that URL already has a fragment; otherwise append the DID fragment (the URL "inherits" it).
- Otherwise dereference the fragment by the resource's media type. For `application/did`, use the `application/ld+json` fragment rules.

The fragment step can run in the client while the resolver handles the resource (Resolution § 8.2.3).

Examples from Resolution § 5.5:

```text
did:example:123456789abcdefghi#keys-1
  → the verification method with that id

did:example:123456789abcdefghi?service=messages&relativeRef=%2Fsome%2Fpath%3Fquery#frag
  with serviceEndpoint "https://example.com/messages/8377464"
  → https://example.com/messages/8377464/some/path?query#frag   (as printed in § 5.5.2)
```

Strict RFC 3986 § 5 resolution of the absolute-path reference `/some/path?query` against that base yields `https://example.com/some/path?query`, not the path the example prints. Test against the algorithm text, and check this example again in later drafts.

### DID URL dereferencing result (§ 10, at risk)

JSON with media type `application/did-url-dereferencing`, using the keys `content`, `didUrlDereferencingMetadata` and `contentMetadata` in the § 10.1 example.

## Errors

Implementers SHOULD encode errors as RFC 9457 problem details. If they do, `type` MUST be a URL, and the codes below are prefixed with `https://www.w3.org/ns/did#`; `title` SHOULD be a short specific string and `detail` a longer one (Resolution § 11).

| Error type                     | Raised when                                                    | HTTP status (§ 12.1) | DID 1.0 keyword              |
| ------------------------------ | -------------------------------------------------------------- | -------------------- | ---------------------------- |
| `INVALID_DID`                  | The DID is not valid (§ 4.4).                                  | 400                  | `invalidDid`                 |
| `INVALID_DID_URL`              | The DID URL is not valid (§ 5.4).                              | 400                  | `invalidDidUrl`              |
| `INVALID_OPTIONS`              | One or more options are invalid.                               | 400                  | none                         |
| `NOT_FOUND`                    | The resolver could not find the DID document.                  | 404                  | `notFound`                   |
| `REPRESENTATION_NOT_SUPPORTED` | The requested `accept` representation is not supported.        | 406                  | `representationNotSupported` |
| `INVALID_DID_DOCUMENT`         | The DID document was malformed.                                | 500                  | none                         |
| `METHOD_NOT_SUPPORTED`         | The resolver does not support the DID's method.                | 501                  | none                         |
| `FEATURE_NOT_SUPPORTED`        | A requested feature is not supported; `detail` SHOULD name it. | 501                  | none                         |
| `INTERNAL_ERROR`               | An unexpected error occurred.                                  | 500                  | none                         |

Verification-method errors such as `INVALID_VERIFICATION_METHOD` and `INVALID_RELATIONSHIP_FOR_VERIFICATION_METHOD` come from CID § 3.5 (Resolution § 11). A specification may define new error types that refine these (Resolution § 11). The DID Resolution Extensions note also lists `methodNotSupported` as a keyword error.

## HTTP(S) binding (Resolution § 12.1)

- Resolvers MUST implement the GET form and MAY implement POST. All HTTPS bindings MUST use TLS; certificates for IP addresses are allowed.
- Start from the resolver endpoint, for example `https://resolver.example/1.0/identifiers/`, and append the DID or DID URL.
- Resolution: send `Accept: application/did-resolution` for the full result, or the `accept` option value to get only the document. Dereferencing: `Accept: application/did-url-dereferencing` for the full result, or the `accept` value for only the content.
- GET with options other than `accept`: the DID or DID URL MUST be URL-encoded (RFC 3986 § 2.1) and the options become query parameters. POST: options go in a JSON body.

```http
GET /1.0/identifiers/did%3Aexample%3A1234?versionId=2 HTTP/1.1
Host: resolver.example
Accept: application/did-resolution
```

Response rules:

- An error in the metadata: the status MUST follow the error table above; unlisted error types get an implementation-defined status.
- `deactivated: true` in document or content metadata: status MUST be `410`.
- `Content-Type: application/did-resolution` (or `application/did-url-dereferencing`): the body MUST be the full result.
- Successful resolution returning only the document: `200`, `Content-Type` MUST equal `contentType` from the resolution metadata, and the body is the document in that representation.
- Successful dereferencing to `text/uri-list`: `303`, a `Location` header with the selected service endpoint URL, and an empty body. Any other content type: `200` with `Content-Type` set from the dereferencing metadata.

## Architecture and trust (Resolution § 8, at risk)

- **Verifiable versus unverifiable resolution.** Resolution is verifiable when the registry is reached in a local trusted environment (for example your own full node), through a trusted remote server over a secure channel, or when the resolver can verify the returned document and metadata (for example a light client). Going through a remote untrusted intermediary, such as a third-party blockchain explorer API, is unverifiable (§ 8.1).
- DID methods SHOULD give guidance on at least one verifiable way to implement Resolve. A method that uses proofs MUST specify how they verify the Resolve result (§ 8.1).
- A simple signature on a DID document or its metadata does not necessarily prove control of the DID or that the document is the right one (§ 8.1; DID 1.0 § 9.2).
- **Bindings.** Prefer local bindings. With a remote binding, use a trusted resolver instance, ideally self-hosted (SHOULD), over a secure channel such as a VPN or mutually authenticated TLS (SHOULD), and consider querying several resolvers and comparing results (§ 8.2).
- **Proxied resolution.** A downstream resolver SHOULD pass on all upstream resolution and document metadata, including proofs, and MAY add its own (§ 8.2.2).
- DID 1.0 § 9.1: no central authority mandates which method specification goes with a method name. If you doubt that a resolver implements a method correctly, look up the registered method specification and choose the resolver on that basis.

## Security and privacy (Resolution § 13, § 14)

- Resolution has no authentication or authorization of its own; anyone can resolve, as with DNS (§ 13.1).
- Caching: a resolver that refuses `noCache: "true"` MUST respond with `FEATURE_NOT_SUPPORTED`, explaining that cache bypass was not allowed. Honouring `noCache` can expose the resolver to denial of service (§ 13.2).
- JSON-LD contexts fetched remotely can be tampered with: use a registry of context files with hashes, and fail if a hash does not match (§ 13.3).
- Not every method keeps old versions, so `versionId` and `versionTime` may not be supported (§ 13.4).
- Methods on distributed ledgers SHOULD say how to tell the network apart from its forks (§ 13.5).
- Detect dereferencing cycles, for example through `controller`, `alsoKnownAs` or service endpoints that are DIDs; track visited identifiers and cap recursion depth (§ 13.6).
- `relativeRef` path traversal: after RFC 3986 § 5 resolution and full percent-decoding, normalize the path and reject results outside the service endpoint's base path, for example with `INVALID_DID_URL`. Literal `../` checks are not enough (§ 13.7.1).
- Normalize query strings at the outermost entry point, before caching or forwarding, and use the normalized DID URL as the cache key (§ 13.7.2).
- Percent-encode caller-supplied parameter values before building a DID URL, then validate them after decoding (§ 13.7.3).
- Privacy: resolvers can log and profile clients. Use resolvers you trust or run, or obscure requests with Oblivious HTTP, a trusted proxy or a trusted cache. HTTP headers such as Referer, Origin, Cookie and Authorization, and caches in between, reduce privacy further (§ 12.1 note, § 14.1). Read each supported method's own privacy section (§ 14.2).

## Checklist

- [ ] The resolver rejects a malformed DID with `INVALID_DID` before contacting any registry.
- [ ] An unsupported method gives `METHOD_NOT_SUPPORTED`; an unsupported option gives `FEATURE_NOT_SUPPORTED`; an invalid option, such as `versionId` together with the mutually exclusive `versionTime`, gives `INVALID_OPTIONS`.
- [ ] A deactivated DID returns `didDocument: null` and `deactivated: true`, and `410` over HTTP.
- [ ] The returned document's `id` equals the requested DID; any other `id` fails.
- [ ] Errors are RFC 9457 objects with `https://www.w3.org/ns/did#` type URLs, and HTTP statuses follow the table.
- [ ] `relativeRef` traversal attempts, duplicate parameters and injected parameters are rejected.
- [ ] Clients of resolvers you do not control also accept the DID 1.0 keyword errors.
