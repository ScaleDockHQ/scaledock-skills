# Levels and tracks

Read this when deciding which SLSA level to claim or require, assigning requirements to the producer, the build platform or the source control system, or assessing a platform. Sources: SLSA v1.2 Tracks, Build Track Basics, Build Requirements, Assessing Build Platforms, Source Requirements and Verified Properties, listed in [Sources](../SKILL.md#sources). Citations name the page and its heading.

## Tracks in SLSA v1.2

SLSA is made of tracks, each made of levels; each track addresses different threats and has its own requirements (Tracks). SLSA v1.2 defines two tracks:

| Track  | Levels | Measures                                                               |
| ------ | ------ | ---------------------------------------------------------------------- |
| Build  | L0–L3  | Trustworthiness and completeness of an artifact's build provenance.    |
| Source | L1–L4  | Trustworthiness and completeness of how a source revision was created. |

Each level implies all levels below it in the same track (Verification Summary, SlsaResult). Levels are not transitive: Build levels cover a single build, with no requirement on the levels of transitive dependencies (FAQ, Why is SLSA not transitive?). To refer to a level precisely, write `SLSA [Track] [Level] ([Version])`, for example `SLSA Build L3 (v1.2)`; a level's high-level meaning never changes after publication (Specification Stages, Versioning).

The draft adds a Build Environment track and a Dependency track; see the preview section of [`versions.md`](versions.md). Do not claim levels on those tracks.

## Build track

| Level    | Requirements (Build Track Basics)                        | Focus                       |
| -------- | -------------------------------------------------------- | --------------------------- |
| Build L0 | None.                                                    | n/a                         |
| Build L1 | Provenance showing how the package was built.            | Mistakes, documentation.    |
| Build L2 | Signed provenance, generated by a hosted build platform. | Tampering after the build.  |
| Build L3 | Hardened build platform.                                 | Tampering during the build. |

Build L1 provenance may be incomplete or unsigned and is trivial to bypass or forge. Build L2 makes forging or evading verification require an explicit attack, and requires the consumer to validate the provenance's authenticity. Build L3 makes it require exploiting a vulnerability beyond most adversaries (Build Track Basics, Build L1–L3).

### Requirement matrix (Build Requirements, Overview)

The build platform MUST strengthen its controls to reach a level, and the producer MUST choose a platform capable of the desired level and implement any controls the platform specifies.

| Implementer    | Requirement                          | L1  | L2  | L3  |
| -------------- | ------------------------------------ | --- | --- | --- |
| Producer       | Choose an appropriate build platform | ✓   | ✓   | ✓   |
| Producer       | Follow a consistent build process    | ✓   | ✓   | ✓   |
| Producer       | Distribute provenance                | ✓   | ✓   | ✓   |
| Build platform | Provenance exists                    | ✓   | ✓   | ✓   |
| Build platform | Provenance is authentic              |     | ✓   | ✓   |
| Build platform | Provenance is unforgeable            |     |     | ✓   |
| Build platform | Isolation: hosted                    |     | ✓   | ✓   |
| Build platform | Isolation: isolated                  |     |     | ✓   |

All implementations MUST use industry security best practices: access controls, secure communications, cryptographic secret management, frequent updates and prompt vulnerability fixes (Build Requirements, Security Best Practices).

### Producer (Build Requirements, Producer)

- **Choose an appropriate build platform.** MUST select one capable of the desired Build level; for Build L3 artifacts, a builder capable of Build L3 provenance.
- **Follow a consistent build process.** MUST build consistently so verifiers can form expectations. MAY give verifiers explicit metadata about the build process. If the package ecosystem requires a configuration file describing the build, MUST complete it and keep it up to date.
- **Distribute provenance.** MUST distribute provenance to consumers, and MAY delegate this to a package ecosystem capable of it. See [`provenance.md`](provenance.md#distributing-provenance).

### Build platform: provenance generation (Build Requirements, Provenance generation)

**Provenance exists (L1+).** MUST identify the output by cryptographic digest and describe how it was produced, in a format acceptable to the ecosystem or consumer. SLSA Provenance is RECOMMENDED; an alternate format MUST carry equivalent information and SHOULD be bi-directionally translatable. Completeness is best effort: contents SHOULD be the same at every level, but a few fields MAY be absent at L1 if prohibitively expensive.

**Provenance is authentic (L2+).**

- Consumers MUST be able to validate authenticity: the signature is valid, and the platform and other trusted entities are identifiable. This SHOULD be a digital signature from a key accessible only to the provenance-generating component. Signing methods that help detect and remediate key compromise (transparency logs, or time stamping) are RECOMMENDED.
- Accuracy: provenance MUST be generated by the control plane, inside the trust boundary named in the provenance, not by a tenant. Its data MUST come from the platform, and the platform MUST have some control against tenant tampering.
- Exceptions a tenant MAY generate: the output names and digests (`subject`), and any field not REQUIRED for Build L2 (for example `resolvedDependencies`). Builders SHOULD document tenant-generated fields.
- Completeness SHOULD be complete, though some external parameters MAY be missing; resolved dependencies are best effort.

**Provenance is unforgeable (L3).**

- Provenance MUST be strongly resistant to forgery by tenants.
- Signing secrets MUST be in a secure management system accessible only to the build service account, and MUST NOT be accessible to the environment running user-defined build steps.
- Every field MUST be generated or verified by the platform in a trusted control plane; user-controlled steps MUST NOT inject or alter content, except the L2 exceptions. Build L3 adds no fields beyond L2.
- External parameters MUST be fully enumerated; resolved dependencies stay best effort.

### Build platform: isolation strength (Build Requirements, Isolation strength)

**Hosted (L2+).** All build steps run on a hosted build platform, not on an individual's workstation.

**Isolated (L3).** Builds run free of unintended external influence, even between builds of the same tenant project. The platform MUST guarantee that:

- a build cannot access platform secrets such as the provenance signing key;
- two overlapping builds cannot influence each other;
- a build cannot persist into or influence a later build's environment: an ephemeral environment MUST be provisioned per build;
- a build cannot poison a cache used by another build: output MUST be identical with or without the cache;
- the platform opens no services allowing remote influence unless every such interaction is captured in `externalParameters`.

Build L3 does not stop a producer running a risky build, and "isolated" is not "hermetic" (no network); hermeticity is a future direction (Build Requirements, Isolated).

### Assessing a build platform (Assessing Build Platforms)

- The adversary's goal is to make provenance claim that external parameters P produced artifact Y when P produces X (Threats, Adversary goal).
- Consumers SHOULD evaluate defence against three adversary profiles: project contributors, project maintainers and build platform administrators (Adversary profiles).
- Consumers SHOULD assess at least five build model elements: external parameters, control plane, build environments, caches and outputs, against the security model behind `builder.id` (Build platform components).
- Organizations may self-attest, publishing their evidence, or seek third-party certification (Builder evaluation).

Build L3 does not cover a compromised platform or a malicious insider; verifiers choose which platforms to trust (Verifying Artifacts, Step 1).

## Source track

| Level     | Requirements (Source Requirements, Basics)              | Focus                                                    |
| --------- | ------------------------------------------------------- | -------------------------------------------------------- |
| Source L1 | Use a version control system.                           | Discrete source revisions for precise consumption.       |
| Source L2 | Preserve change history and generate source provenance. | Reliable history through enforced controls and evidence. |
| Source L3 | Enforce organizational technical controls.              | Consumer knowledge of guaranteed technical controls.     |
| Source L4 | Require code review.                                    | Code quality and resistance to insider threats.          |

Onboarding a branch, or raising its level, makes claims from that revision forward only; no claims cover prior revisions (Source Requirements, Onboarding).

### Organization (Source Requirements, Organization)

- **L1+:** MUST select a source control system (SCS) capable of the desired Source level.
- **L2+:** MUST restrict sensitive operations through the SCS's identity management; MUST configure a reliable change history (or show continuous enforcement); if tags are supported, MUST prevent moving or deleting them.
- **L2+, safe expunging:** MAY expunge content only for legal or privacy compliance; MUST document the process and SHOULD log removals; SCSs SHOULD require an administrator plus one more trusted person.
- **L3+:** MUST provide evidence of continuous enforcement for every claim in source provenance or VSAs, and MUST document what each control means.

### Source control system (Source Requirements, Source Control System)

- **L1+:** repositories MUST have a stable unique locator; revisions MUST be immutable and unique in the repository, and non-digest IDs need documented immutability; MUST show human-readable diffs for plain text; MUST issue a Source VSA for every revision at L1 or above, fetchable by anyone authorized to read the revision. With no Source VSA, the revision is Source L0.
- **L2+:** MUST record every change to named references (when, who, new revision); a branch MUST only move to descendants of its current revision (in git, no force push); MUST track continuity per claimed control from a start revision and re-establish it after a lapse; MUST provide identity management and document attribution; MUST produce source provenance contemporaneously, and from L2 Source VSAs MUST be based on it.
- **L3+:** MUST let the organization mark protected named references and enforce controls on them; MUST record enforced controls in contemporaneous attestations; MUST restrict organization properties to the `ORG_SOURCE_` prefix.
- **L4:** changes to protected branches MUST be agreed by two or more trusted persons before submission, the final revision included; approvals are per context; reviewers MUST see a clear representation of the result. Trusted robots MAY get a perpetual exception.

The Source VSA format and the source verification steps are in [`verification.md`](verification.md#verifying-source-revisions).

## Verified properties (Verified Properties)

Properties that do not fit a level MAY appear in a VSA's `verifiedLevels` when the issuer determines their requirements are met:

- `SLSA_SOURCE_TWO_PARTY_REVIEWED`: MUST only be issued per the Source track's two-party review requirement, at any Source level.
- `SLSA_BUILD_REPRODUCED`: MUST only be issued if the artifact has build provenance from two or more independently operated build platforms trusted by the VSA issuer.
