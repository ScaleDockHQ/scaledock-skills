# List header fields

Read this when choosing, writing or parsing the `List-*` header fields. Section numbers refer to RFC 2369 unless another RFC is named.

## Common rules for the RFC 2369 fields

- The fields are optional; a list may implement only one or two (§ 1). `List-Help` is the most useful single field, because it can point to instructions for every other command (§ 1, § 3.1).
- Generators SHOULD usually include a `mailto:` command in addition to any other protocol, for users without web access (§ 1).
- Values follow the encoding and character rules for mail headers, and URLs are limited to URL-safe characters (§ 2).
- A value is mostly angle-bracketed URLs; whitespace inside the brackets is ignored. MTAs MUST NOT insert whitespace inside the brackets; clients treat any that appears as characters to ignore (§ 2).
- Several alternative URLs MAY be listed, comma-separated, in order of preference from left to right (§ 2).
- Commands that need client-filled variables, such as the user's address, are not supported. Lists that need them SHOULD still use `List-Help` to give instructions or a structured interface such as an HTML form (§ 2, Appendix A.5).
- The fields a list implements SHOULD be on every message it distributes, including command responses to individual users, and on other messages that clearly apply to one list (§ 3).
- There MUST be no more than one of each field in a message (§ 3).
- The fields MUST only be generated by mailing lists, not end users (§ 3), and list processors should not pass user-originated list header fields through (§ 5).
- Comments in parentheses are allowed around the URLs, as the examples in § 3 show.

## The fields

| Field              | Meaning                                                                                      | Section |
| ------------------ | -------------------------------------------------------------------------------------------- | ------- |
| `List-Help`        | Where to get help or instructions for the list; the most important field.                    | § 3.1   |
| `List-Unsubscribe` | The command (preferably mail) that directly removes the user from the list.                  | § 3.2   |
| `List-Subscribe`   | The command (preferably mail) that directly subscribes the user.                             | § 3.3   |
| `List-Post`        | How to post to the list; may be a moderator. The special value `NO` means posting is closed. | § 3.4   |
| `List-Owner`       | How to reach a human administrator; unnecessary if that is the postmaster.                   | § 3.5   |
| `List-Archive`     | How to access the list archives.                                                             | § 3.6   |

Examples from the RFC:

```text
List-Help: <mailto:list@host.com?subject=help> (List Instructions)
List-Help: <http://www.host.com/list/>, <mailto:list-info@host.com>
List-Unsubscribe: <mailto:list@host.com?subject=unsubscribe>
List-Unsubscribe: <http://www.host.com/list.cgi?cmd=unsub&lst=list>,
    <mailto:list-request@host.com?subject=unsubscribe>
List-Subscribe: <mailto:list-request@host.com?subject=subscribe>
List-Post: <mailto:moderator@host.com> (Postings are Moderated)
List-Post: NO (posting not allowed on this list)
List-Owner: <mailto:listmom@host.com> (Contact Person for Help)
List-Archive: <http://www.host.com/list/archive/> (Web Archive)
```

The RFC's examples use `http:`; for one-click, `List-Unsubscribe` needs an `https:` URI (RFC 8058 § 3.1). Using these fields does not remove the requirement to support the `-request` command address for lists (§ 1).

## `List-Unsubscribe-Post` (RFC 8058)

```abnf
fields =/ list-unsubscribe-post
list-unsubscribe-post = "List-Unsubscribe-Post:" 0*1WSP postarg CRLF
postarg = "List-Unsubscribe=One-Click"
```

- RFC 8058 § 5 imports `fields`, `WSP` and `CRLF` from RFC 5322. The value is the single literal key/value pair, with at most one whitespace character before it.
- The value is limited to that one known pair so an attacker cannot craft a message whose POST fills in an arbitrary form on a victim website (§ 6).
- It only has meaning together with a `List-Unsubscribe` field that contains one HTTPS URI (§ 3.1), and both are covered by a valid DKIM signature (§ 4).

A complete one-click header block, from RFC 8058 § 8.2:

```text
List-Unsubscribe:
    <mailto:listrequest@example.com?subject=unsubscribe>,
    <https://example.com/unsubscribe.html?opaque=123456789>
List-Unsubscribe-Post: List-Unsubscribe=One-Click
```

## `List-Id` (RFC 2919)

```abnf
list-id-header = "List-ID:" [phrase / CFWS] "<" list-id ">" CRLF
list-id = list-label "." list-id-namespace
list-label = dot-atom-text
list-id-namespace = domain-name / unmanaged-list-id-namespace
unmanaged-list-id-namespace = "localhost"
domain-name = dot-atom-text
```

The header line includes the correction from verified erratum EID 3951; `phrase`, `CFWS` and `dot-atom-text` come from RFC 2822 (erratum EID 2499).

- The identifier looks like a host name in a domain of the list owner. The owner MUST NOT generate identifiers in a domain namespace they have no authority over (RFC 2919 § 2).
- Owners without a domain may use the unmanaged `localhost` namespace (§ 2). They SHOULD add the creation month and year as `MMYYYY`, and part of the identifier MUST be random, SHOULD be 128 bits as 32 hex characters (§ 5).
- A `list-id` MUST NOT be longer than 255 octets (§ 2).
- Identifiers not ending in `.localhost` MUST be globally unique (§ 5). A `list-id` subdomain, such as `list-id.example.com`, is suggested but not required (§ 5).
- The header SHOULD be on every message the list distributes, including command responses, there MUST be at most one, and only list software generates it (§ 3).
- An optional description goes in the `phrase` before the brackets; free whitespace and comments around tokens are otherwise not allowed (§ 3).
- The administrator SHOULD avoid changing the identifier, even when the host changes; moving from `localhost` to a domain namespace is an acceptable reason (§ 4).

Examples from RFC 2919 § 3:

```text
List-Id: List Header Mailing List <list-header.nisto.com>
List-Id: <commonspace-users.list-id.within.com>
List-Id: "An internal CMU List" <0Jks9449.list-id.cmu.edu>
List-Id: <da39efc25c530ad145d41b86f7420c3b.052000.localhost>
```

## Nested lists

- A sublist SHOULD remove the parent's `List-Help`, `List-Subscribe`, `List-Unsubscribe` and `List-Owner`, and SHOULD insert its own (RFC 2369 § 4).
- If the sublist has its own archive it SHOULD replace `List-Archive`; otherwise it MUST leave it untouched (RFC 2369 § 4).
- The sublist MAY replace `List-Post`, but should not change it so that postings reach only sublist members when they are meant for the whole primary list (RFC 2369 § 4).
- A sublist MUST NOT modify `List-Id`; a list processor that meets a `List-Id` from an unexpected source SHOULD NOT pass it through (RFC 2919 § 7).
- When a sublist replaces `List-Unsubscribe` on a message that also carries `List-Unsubscribe-Post`, the new pair has to be covered by a DKIM signature the sublist applies (RFC 8058 § 4); see the `dkim` skill.

## IANA registration

The IANA Message Headers registry (last updated 2026-05-13) lists `List-Archive`, `List-Help`, `List-ID`, `List-Owner`, `List-Post`, `List-Subscribe` and `List-Unsubscribe` as permanent mail header fields with RFC 4021 as the reference, and `List-Unsubscribe-Post` with status standard and RFC 8058 as the reference (RFC 8058 § 7).
